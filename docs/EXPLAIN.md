## 1. 全貌

我們要在 Tang Nano 20K 這塊 FPGA 開發板上，做一個**脈衝神經網路（spiking neural network）**。

- **神經元模型**：LIF（Leaky Integrate-and-Fire，漏電整合發放）。它是神經科學裡最簡單的神經元模型之一。
- **為什麼用 FPGA**：每一顆神經元的計算很簡單，但要模擬很多顆、而且要即時跑，用 CPU 慢。FPGA 可以把計算做成電路，多顆神經元平行運作。
- **最終目標**：256 顆神經元組成的網路，能跑興奮／抑制（E/I）平衡實驗，之後用來研究擾動如何改變網路行為。

整個流程分成幾層，互相對照：

```
Python 參考模型 (model/fixed.py)     ← 規格：每個數值怎麼算，以它為準
        │ 逐位元比對
        ▼
Verilog 硬體 (rtl/*.v)               ← 在 FPGA 上真的算
        │ UART 串列傳輸（115200 baud）
        ▼
PC 端程式 (host/*.py)                ← 下指令、讀結果、畫圖
```

**核心原則：Python 模型是規格，硬體必須逐位元符合它。** 不能只說「看起來差不多」。每次改硬體，都要跑比對測試。

## 2. 理論

### 2.1 LIF 神經元

真實神經元會累積輸入電流，電位超過某個門檻就「發放」一個脈衝（spike），然後電位被重置。LIF 把這個過程簡化成兩個變數：

- **V**（膜電位）：神經元內部的電位，會隨時間慢慢往靜止值 V_rest 回歸（這就是「洩漏」，leak）。
- **I**（突觸電流）：來自其他神經元或外部輸入的電流，會逐漸衰減。

用離散時間（每一步是一個時脈週期或一個時間單位）寫出來，就是本專案的規格（見 `model/fixed.py` 的 `step()`）：

```
I[t+1] = I[t] − (I[t] >> k_s) + input            ← 電流衰減，再加入新輸入
V[t+1] = V[t] + ((V_rest − V[t]) >> k_m) + I[t+1]  ← 向靜止值洩漏，再加上電流
若 V[t+1] ≥ θ（閾值）：發放（spike = 1），V 重置為 V_reset，進入不反應期
```

每一項的意思：

- `(V_rest − V) >> k_m`：V 離靜止值越遠，回拉越多。`>> k_m` 代表乘以 2^(−k_m)，也就是時間常數 τ 的倒數（dt/τ = 2^(−k_m)）。
- `I >> k_s`：電流同樣乘以 2^(−k_s) 衰減。
- **不反應期（refractory period）**：發放後的幾步內，神經元不能再發放，即使電位夠高。真實神經元也是這樣，而且它會限制最高發放率。

### 2.2 f-I 曲線

f-I 曲線描述「輸入電流 I 越大，發放率 f 越高」的關係。它是神經元最基本的特性之一。

我們在 `docs/fi_curve.png` 畫了兩條線：浮點版和定點版。兩條線形狀一致，最大差異是 0.027 spikes/step。曲線呈階梯狀，主要有兩個原因：

1. 不反應期限制了最高發放率（離散的步數）。
2. 位移運算 `>>` 會把很小的值變成 0，形成「死區」，在閾值附近特別明顯。

### 2.3 為什麼用定點數而不是浮點數

FPGA 處理浮點數很佔資源。我們改用 **Q8.8 定點數**：

- 一個 16-bit 有號整數，代表實數 `raw / 256`。例如 `raw = 384` 代表 1.5。
- 範圍大約是 −128 到 127.996，精度是 1/256。
- 加法就是整數加法；乘以 2 的負次方就是算術右移 `>>`。**不需要乘法器**。

這是 D-001（見 `docs/DECISIONS.md`）。代價是小於 1/256 的變化會被量化掉。

### 2.4 飽和與算術位移（兩個容易出錯的地方）

**飽和（saturation）**：每次加法後，結果超出 [−32768, 32767] 就夾到邊界，而不是繞回。

- 為什麼：如果繞回，一個很大的興奮輸入會變成很大的抑制值，造成難以察覺的錯誤。
- 規則是「逐次加法後飽和」，也就是從左到右，每一次加法都夾一次。這和 RTL 的實作順序必須一致，否則結果會不同。

**算術位移（arithmetic shift）**：`>>` 對有號數會保留符號位元。

- 負數右移後仍然是負數（向負無限方向取整）。
- 邏輯右移會把符號位元補 0，負的膜電位衰減時會變成很大的正數。這是常見錯誤。
- 在 Verilog 裡，要用 `>>>`，而且變數要宣告 `signed`。

### 2.5 為什麼需要 17-bit 的中間值

計算 `V_rest − V` 時，兩個 16-bit 有號數相減可能超出 16-bit 範圍（例如 32767 − (−32768) = 65535）。所以 RTL 必須用 17-bit 或更寬的中間值，否則在極端輸入下得到錯誤的洩漏量。這是 D-004。

`-(I >>> 0)` 也有同樣問題：當 I = −32768 時，取負會超出 16-bit，所以 `lif_core.v` 用 18-bit 運算。

### 2.6 驗證的基本思想

- **規格先行**：先在 Python 寫出精確的定點模型，它是唯一的標準。
- **逐位元比對**：硬體與模型在同樣的輸入下，輸出必須完全相同（不是「接近」）。
- **隨機測試加上邊界測試**：隨機輸入能覆蓋一般情況，邊界（最大值、最小值、剛好等於閾值、不反應期中有輸入）則專門找最容易出錯的地方。
- **變異測試（mutation testing）**：故意把程式改壞（例如把 `>>>` 改成 `>>`），確認測試會抓到。如果測試沒有失敗，代表測試本身沒有用。我們對 BSRAM 檢查器、`lif_core`、命令解碼器都做過這個檢查。UART 目前只有正向模擬測試，還沒有做變異測試。

## 3. 硬體與工具

### 3.1 FPGA 的基本概念

FPGA（Field-Programmable Gate Array）是一塊可以重新接線的晶片。它的主要資源：

- **LUT（查找表）**：一個小型記憶體，可以實現任何 4 輸入（或更多）的組合邏輯函數。
- **FF（正反器，flip-flop）**：儲存一個位元，在時脈上升沿更新。這是「循序邏輯」的基礎。
- **BSRAM（塊狀記憶體）**：晶片內建的大塊 RAM，比用 FF 組成的記憶體省資源。GW2AR-18 大約有 46 塊，共約 828 Kbit。
- **時脈（clock）**：板子提供 27 MHz。每個時脈週期，所有 FF 同步更新一次。

**組合邏輯與循序邏輯**：組合邏輯的輸出只依賴目前的輸入（例如 `lif_core.v`，它是純組合電路）；循序邏輯的輸出還依賴內部狀態（例如 `uart_tx.v` 的狀態機）。

### 3.2 Verilog 的兩種寫法

- `assign` 或 `always @(*)`：組合邏輯。
- `always @(posedge clk)`：循序邏輯，在時脈上升沿更新。這裡要用非阻塞賦值 `<=`，讓所有 FF 同時更新，避免讀到舊值的混亂。

我們的程式全部使用 `<=` 做循序更新。

### 3.3 Tang Nano 20K

- 晶片：Gowin GW2A(R)-18，我們用 JTAG 讀到的 idcode 0x81b 確認了型號。
- 時脈：27 MHz，接在 pin 4。
- LED：六顆，接在 pin 15–20，**低電位點亮**（所以程式輸出 `~state`）。
- USB 介面：板上的 BL616 晶片負責 USB 與兩個 FTDI 通道。一個通道走 JTAG（用來燒錄），另一個通道走 UART（用來和 FPGA 通訊）。我們用實測確認：`/dev/ttyUSB1` 能和 FPGA 回送，所以它是 UART 通道。
- **燒錄到 SRAM**：`openFPGALoader` 把 bitstream 寫入 FPGA 的 SRAM，斷電後消失。這是我們現在使用的方式，適合開發。

### 3.4 工具鏈

整條流程在 WSL（Ubuntu）裡用 OSS CAD Suite 完成：

```
Verilog ──yosys (synth_gowin)──▶ 網表 (.json)
        ──nextpnr-himbaechel──▶ 佈局佈線 (place & route)，並做時序分析（最高頻率）
        ──gowin_pack──────────▶ bitstream (.fs)
        ──openFPGALoader──────▶ 寫入板子
```

- **yosys**：把 Verilog 轉成電路網表。
- **nextpnr**：決定每個邏輯放在晶片哪裡，並檢查時序是否能跑在 27 MHz。
- **gowin_pack**：把結果打包成板子能讀的檔案。
- **Icarus Verilog（iverilog）**：模擬器，用來跑測試台（testbench）。
- **cocotb**：用 Python 寫測試，驅動 Verilog 模擬。目前 `lif_core` 用 cocotb 比對。

`fpga/Makefile` 把這些串起來：`make TOP=<名稱>` 建置，`make flash TOP=<名稱>` 燒錄。

## 4. 各模組說明

### 4.1 `model/fixed.py`：定點模型（規格）

- 定義 `sat()`（飽和）、`sadd()`（逐次加法後飽和）、`step()`（一步更新）、`Params`（參數，有範圍檢查）、`run()`（跑一串輸入）。
- **為什麼 `Params` 要檢查範圍**：`refrac` 是 3-bit（0–7），`k_m`、`k_s` 是 4-bit 位移量（0–15）。硬體只有這麼多位元，超出範圍的參數在硬體上會被截斷，結果就錯了。所以模型一開始就拒絕它們。
- `to_q()`：把實數轉成 Q8.8，四捨五入後飽和。

### 4.2 `model/lif.py`：浮點版

- 和定點版用同樣的方程式，但用浮點數、沒有飽和。
- 用途：比較形狀。定點版和浮點版的 f-I 曲線應該接近，差異來自量化。

### 4.3 `model/test_fixed.py`：10 個單元測試

測試飽和、逐次飽和、算術位移的取整方向、Q8.8 轉換、無輸入、發放、不反應期間隔、兩端飽和、抑制降低發放率。全部通過。

### 4.4 `model/fi_curve.py`：產生 f-I 曲線圖

掃描一系列輸入電流，分別用浮點與定點算發放率，畫成 `docs/fi_curve.png`。

### 4.5 `rtl/lif_core.v`：單顆神經元（組合邏輯）

這是 `fixed.py` 的 `step()` 的硬體版。它是**純組合電路**：輸入目前狀態和輸入電流，輸出下一步狀態和 spike，不需要時脈。

關鍵實作細節：

- **中間值用 18-bit 有號數**：避免 −32768 取負、`V_rest − V` 溢出（見 2.5）。
- **飽和函式 `sat16`**：檢查 18-bit 結果是否超出 16-bit 範圍，超出就夾住。
- **算術位移 `>>>`**：宣告 `signed`，保留符號。
- **不反應期**：`ref_cnt > 0` 時，V 強制設為 V_reset，計數器遞減，不發放。
- **發放判斷**：`fire = ~in_ref & (v_new >= theta)`，只有不在不反應期且超過閾值才發放。

**驗證**：10,000 組隨機輸入 + 110 組定向測試（飽和、閾值 ±1、k_s = 0、k_m = 0、refrac = 0 與 7 等）+ 15 條 500 步的多步軌跡，全部和 `fixed.py` 逐位元一致。把洩漏的 `>>>` 改成 `>>`，測試立即失敗。

**為什麼是組合電路**：單一神經元的計算很短，組合電路就能做完。之後會在排程器裡用時脈分時共用這個電路，服務 256 顆神經元（M3）。

**命名注意**：原本的輸入埠叫 `ref`，但在 SystemVerilog 裡 `ref` 是保留字，所以改名為 `ref_cnt`。

### 4.6 `rtl/uart_tx.v`：UART 發送器

UART 是最簡單的串列協定之一，一個 byte 的格式是：

```
閒置(高) │ 起始位(低) │ D0 D1 D2 D3 D4 D5 D6 D7（LSB 先送）│ 停止位(高) │ 閒置
           ←──────────────────── 一個 byte = 10 個位元時間 ────────────────────→
```

這裡用 **8N1**：8 個資料位元、無同位元、1 個停止位元。

- **分頻**：`CLK_DIV = round(27 MHz / 115200) = 234`，每個位元持續 234 個時脈。實際鮑率是 115384.6，誤差 +0.16%。UART 對這點誤差有容忍度（大約 ±2%），所以沒問題。
- **握手**：`start` 是一個單週期脈衝，只在 `busy` 為低時被接受。忙碌時的 `start` 會被忽略。`busy` 在停止位元結束的那個時脈降為低。
- **移位暫存器**：`{停止位, 資料, 起始位}` 組成 10 bit，每個位元時間右移一位，從 LSB 依序送出。

### 4.7 `rtl/uart_rx.v`：UART 接收器

接收端的關鍵問題是：**發送端和接收端的時脈不同步**，接收器必須自己找到每個位元的中央來取樣。

- **兩級同步器**：`rx` 來自外部，和 FPGA 的時脈沒有關係。直接使用可能讓 FF 進入亞穩態（metastability）。所以先經過兩個 FF（`rx_sync`）再使用。這是標準做法。
- **偵測起始位**：`rx` 由高變低時，開始計時。
- **起始位確認**：等到起始位中央（半個位元時間）再檢查一次。如果仍是低，才確認是真正的起始位，否則視為雜訊丟棄。
- **資料取樣**：每隔一個完整位元時間取樣一次，正好在每個位元的中央，離邊界最遠，最不容易出錯。
- **停止位檢查**：停止位不是高，就丟棄這一幀（framing error）。

**模擬驗證**（6/6 通過）：背靠背 10,000 bytes、2,000 bytes 隨機空閒、全部 256 個值、外部傳送速率偏差 0.96–1.04 倍的容忍度，以及忙碌時 start 被忽略。

### 4.8 `rtl/uart_echo.v`：回送（上板 UART 測試）

把 `uart_rx` 收到的 byte 原樣交給 `uart_tx` 送回去。

- **為什麼需要一個 byte 的暫存（holding register）**：接收完一個 byte 的那一刻，發送器可能還在送前一個 byte。如果新 byte 直接丟給發送器，會被忽略。暫存器讓它等一下。
- 同一時脈上，`rx_valid` 的優先權高於清除 `pending`，因為兩者都用「這個時脈之前」的值，行為一致。

**上板結果**：
- `/dev/ttyUSB1` 回送 4/4 通過，連跑兩次一致。
- 一次連續送出超過約 64 bytes 會丟資料，原因不在 FPGA，而在 USB–UART 橋接晶片（見 4.13）。
- 10,000 bytes 按 16-byte 分段送出，0 錯誤。使用者已確認這算通過 M1 的 UART 驗收。

### 4.9 `rtl/bsram_test.v`：BSRAM 自測

BSRAM 是晶片內建的記憶體。這個測試檢查「我們寫的 RAM 在硬體上是否真的正確運作」。

- 寫入 256 個 16-bit 圖樣，`pattern(a) = {a, ~a} ^ 0x5AA5`，然後逐一讀回比對。
- **同步讀取**：BSRAM 的讀取要等一個時脈才出現在輸出，所以狀態機要處理 `rd_valid`。
- 結果用 LED 顯示：`status = {errors, fail, pass, done}`，LED 低電位點亮。PASS 時應該是同一側的兩顆亮。
- 模擬通過（515 個時脈），故意寫錯一個字時測試會報 FAIL。
- 合成時 yosys 把 256×16 的記憶體映射成一個 `SPX9` BSRAM 原語，證明我們的寫法會真的用到 BSRAM。
- **限制**：目前只有 LED 顯示結果，沒有逐字回傳比對。

### 4.10 `rtl/blink.v`：LED 閃爍

最簡單的上板測試，用來驗證時脈、腳位、燒錄流程。六顆 LED 每 0.5 秒整組切換。使用者已確認閃爍。

### 4.11 `host/protocol.py`：PC–板子的封包格式

PC 和板子之間的所有指令，都用同一種封包：

```
[0xA5][cmd][len][data … len bytes][checksum]
checksum = (cmd + len + Σdata) mod 256
```

- **0xA5 是同步位元組**：接收端看到它才開始解析，所以可以從任何位置開始接收。
- **len 是資料長度**：接收端依長度讀取資料，不需要結束符號。這樣資料本身可以包含任何數值（包括 0xA5）。
- **checksum**：偵測傳輸錯誤。它很簡單（只做加總），抓得到單一位元錯誤，但抓不到所有錯誤（例如兩個位元互換）。這個限制已記在 D-007。
- **多位元組值用 little-endian**：低位元組在前。Q8.8 數值是有號 16-bit，權重是有號 8-bit。

**`FrameParser`（增量解析器）**：PC 收到的資料可能分段到達，也可能夾雜雜訊。解析器會：
- 累積資料，直到一個完整封包到齊。
- 忽略同步位元組之前的垃圾資料。
- 遇到校驗錯誤的封包時，只跳過那個 0xA5，然後從下一個 0xA5 重新開始。

**測試**：`host/test_protocol.py` 有 33 個測試（加入 READ_TRACE 之後），包括已知向量、長度邊界（0 到 255）、壞 checksum、長度不符、資料中含 0xA5、逐位元組餵入、壞封包後重新同步、數值範圍檢查。全部通過。

**命令代碼**（見 D-007）：

| 代碼 | 名稱 | 用途 |
|---|---|---|
| 0x01 | WRITE_PARAM | 寫入神經元參數（θ、V_reset、V_rest、k_m、k_s、refrac） |
| 0x02 | WRITE_WEIGHTS | 寫入突觸權重 |
| 0x03 | SET_INPUT | 設定輸入電流或雜訊 |
| 0x04 | RUN | 執行 T 步，把紀錄存在板上 |
| 0x05 | READ_RECORD | 讀回紀錄 |
| 0x06 | READ_STATUS | 讀取執行狀態與錯誤旗標 |
| 0x07 | READ_COUNTS | 網路版：讀取每顆神經元的發放次數（4.18） |
| 0x08 | READ_SNAPSHOT | 網路版：讀取最後一步的 V 與 spike（4.18） |
| 0x09 | READ_TRACE | 網路版：讀取前 512 步的 spike 軌跡（4.20） |

回應沿用同一格式，cmd 的最高位元設為 1（0x80）。READ_STATUS 的回應（0x86）已經實作，見 4.15 與 4.18。`pack_read_trace` 拒絕「起始 + 數量 > 512」，`unpack_trace` 拒絕 n ≤ 0。

**跑測試的範圍**：`host/pytest.ini` 讓 pytest 只收集 `test_*.py`，這樣 pytest 不會匯入板上的腳本（它們不是測試）。在 `host/` 目錄執行 `python -m pytest` 即可。

**為什麼用這種協定**：計畫書指定了外型。checksum 與位元組序是我選的，已由作者審閱（D-007）。

### 4.12 `rtl/cmd_decoder.v`：FPGA 端的封包解碼器

這是 `protocol.py` 的硬體版。它接收 uart_rx 送來的 byte 串流，依照封包格式解析，驗證通過後才改變參數。

**狀態機**（五個狀態）：

```
S_SYNC ──(0xA5)──▶ S_CMD ──▶ S_LEN ──(len=0)──────────────▶ S_CSUM
                              │                                 ▲
                              └──(len>0)──▶ S_DATA ──(收完)────┘
                                                                 │
                                    比對 checksum，通過才提交 ◀──┘
                                    回到 S_SYNC
```

- **S_SYNC**：忽略所有非 0xA5 的位元組。
- **S_CMD**：記錄 cmd，開始累加 checksum。
- **S_LEN**：記錄長度，把它加入 checksum。長度為 0 時直接跳到 S_CSUM。
- **S_DATA**：把資料存進緩衝（整個 payload，最多 255 bytes；網路指令需要較長的封包，見 4.18），同時累加 checksum。
- **S_CSUM**：比對接收到的 checksum 與累加結果。

**先驗證，後提交**：參數只在 checksum 通過時才寫入。這樣一個損壞的封包不會改變正在運作的神經元參數。這是這個模組最重要的設計。

**提交前的檢查**（WRITE_PARAM）：
- 長度必須是 9。
- k_m ≤ 15、k_s ≤ 15、refrac ≤ 7。這和 `model/fixed.py` 的 `Params` 檢查一致，超出範圍的值會被拒絕。

**計數器**：`ok_count` 記錄接受的封包數，`err_count` 記錄拒絕的封包數（checksum 錯、未知命令、數值超出範圍）。兩者都會在 255 時繞回。

**RUN 與 READ_RECORD**（M2 加入）：
- `RUN`（0x04）帶 4 bytes：輸入電流（Q8.8，2 bytes）與步數（1..1024，2 bytes）。有效時送出 `run_req` 脈衝，並把輸入與步數存起來。
- `READ_RECORD`（0x05）帶 3 bytes：起始步（2 bytes）與數量（1..64）。只有在「數量 ≥ 1、且起始 + 數量 ≤ 上一次 RUN 的步數」時才有效。
- **忙碌時拒絕**：`busy` 為高時，命令會被拒絕並計入 err。在單顆神經元版本，`busy` 只代表回覆正在傳送，所以 STATUS、RUN、READ_RECORD 被拒絕。網路版（4.18）的 `busy` 還包括網路執行與權重載入中，因此 WRITE_PARAM 也受保護（M2 版原本沒有這個限制，改動後 `neuron_top` 的上板測試與模擬都重跑過，仍然通過）。原因：回覆是從記錄記憶體讀出的，如果這時新的 RUN 開始，記憶體會被覆寫，回覆就會混入新舊資料。第一版設計沒有這個保護，模擬時就抓到了（見 4.16）。

**已知限制**：
- **沒有逾時機制**。如果長度欄位損壞，解碼器會等錯誤的位元組數，之後的封包都會錯位。PC 端要用已知的起點重新同步。
- **不能加逾時**：UART 橋接晶片的分段送出會在封包中間停頓約 2 ms，如果逾時太短，正常的封包會被誤判。這個限制是在測試 10,000 bytes 時發現的。
- **回應由頂層產生**：解碼器只負責解析與提交參數。READ_STATUS 時它送出 `status_req` 脈衝，回覆封包由 `cmd_test.v`（見 4.15）組出並送出。其他命令目前還沒有回應。

**驗證**：
- `host/gen_cmd_vectors.py` 用 `protocol.py` 產生一段 59 bytes 的串流，內含：一個有效封包、一個 checksum 錯誤的封包、一個未知命令、一個 k_m 超出範圍的封包、一段前置垃圾，最後是另一個有效封包。
- `sim/tb_cmd_decoder.v` 餵入這段串流，檢查最後的參數與計數器。結果：PASS（ok=2，err=3），參數等於第二個有效封包的值。
- **這是跨語言的比對**：封包是 Python 產生的，解碼器是 Verilog 寫的，兩邊用的是同一份格式規格。如果任一邊的格式錯了，測試會失敗。
- 變異測試：關掉 checksum 檢查，或拿掉 k_m 範圍檢查，測試都會失敗（計數器不符）。
- yosys 合成成功，約 210 cells，其中 182 個 FF。緩衝區沒有用 BSRAM，因為它很小。

### 4.13 `host/uart_loopback.py`：上板 UART 測試

- 用 Python 標準函式庫的 `termios` 設定串列埠為 115200 8N1，不需要額外套件。
- 測試案例：一次寫入的短突發（16、64 bytes）、分段節流的長資料（256、1,000、10,000 bytes）。
- **為什麼要分段節流**：USB–UART 橋接晶片（BL616）沒有流控（RTS/CTS），緩衝很小。PC 以 USB 速度寫入，橋接晶片以 115200 baud 轉送給 FPGA，超出緩衝的部分就會丟失。實測：一次寫入 96 或 128 bytes 只回來 66 bytes。
- 解法是按 16-byte 分段寫入，每段之後等待約一個線速的時間。
- **判斷**：這是橋接晶片的限制，不是 FPGA 的問題。FPGA 端按線速接收的測試全部通過。但我沒有直接觀察 FPGA 的接收計數，所以「丟在橋接晶片」仍是推論。

### 4.14 `host/gen_cmd_vectors.py`：產生解碼器測試資料

用 `protocol.py` 編碼封包，輸出給 Verilog 測試台的檔案（解碼器一組，頂層一組）：
- `sim/cmd_stream.mem`：要餵給解碼器的 byte 串流。
- `sim/cmd_expect.mem`：期望的最終參數與計數器值。

期望值是從第二個有效封包的**原始參數**算出來的，不是從解碼器的輸出反推，所以測試不是循環論證。

### 4.15 `rtl/cmd_test.v` 與 `host/board_cmd_test.py`：上板命令鏈測試

這是第一次讓電腦和板子之間的**雙向**通訊都經過協定：電腦送指令，板子解析，再把狀態回傳給電腦。

**頂層結構**：

```
rx ─▶ uart_rx ─▶ cmd_decoder ─▶ 回覆產生器 ─▶ uart_tx ─▶ tx
                     │ status_req（READ_STATUS 時一個脈衝）
                     ▼
              複製參數與計數器，組成 15 bytes 回覆
```

- **回覆封包**：`[0xA5][0x86][0x0B][11 bytes 資料][checksum]`。資料依序是 θ、V_reset、V_rest（各 2 bytes，little-endian）、k_m、k_s、refrac、ok、err。0x86 = 0x06 | 0x80（回應標記）。
- **為什麼要複製一份**：回覆要花約 1.3 ms 才送完（15 bytes × 87 µs），這段時間如果新封包改了參數，回覆就會混著新舊值。複製一次可以保證回覆內容自洽。
- **checksum 在頂層算**：規則和解碼器相同，就是 (cmd + len + Σdata) mod 256。8-bit 加法本身就會 mod 256，所以不需要額外處理。
- **送出方式**：`uart_tx` 空閒時，每個時脈最多送一個 byte。`tx_start` 是單週期脈衝，符合 `uart_tx` 的握手規則（見 4.6）。
- **LED**：led[2:0] 顯示 ok_count 的低 3 位，led[5:3] 顯示 err_count 的低 3 位。LED 低電位點亮，所以輸出 `~{...}`。這讓你不用電腦也能看到計數在變。

**模擬（`sim/tb_cmd_test.v`）**：
- 以位元級別餵入 `top_stream.mem`（17 bytes：一個有效 WRITE_PARAM 加上 READ_STATUS），取樣 tx 上的 15 bytes，逐 byte 與 Python 產生的期望回覆比對。
- 結果：PASS。
- 變異測試：把回覆的 checksum 加 1，測試立即 FAIL（第 14 個 byte 期望 `1f`，得到 `20`）。

**上板（`host/board_cmd_test.py`）**：依序送出 5 個指令，每個之後都用 READ_STATUS 讀回並檢查：

| 步驟 | 送出 | 預期 |
|---|---|---|
| 1 | 有效 WRITE_PARAM | 參數更新，ok +1 |
| 2 | checksum 錯的 WRITE_PARAM | 參數不變，err +1 |
| 3 | k_m = 16 的 WRITE_PARAM | 參數不變，err +1 |
| 4 | 未知命令 0x7E | 參數不變，err +1 |
| 5 | 第二個有效 WRITE_PARAM | 參數更新，ok +1 |

**結果：5/5 PASS**（`/dev/ttyUSB1`）。

**一個容易忽略的細節**：READ_STATUS 本身也是一個有效封包，所以每讀一次，ok 就會加 1。我第一次寫腳本時漏了這一點，所有檢查都對不上。硬體的行為是對的，錯在測試的期望值。修正後 5/5 通過。這也提醒我們：測試的期望值要用獨立的邏輯推算，不能只跟著硬體的輸出走。

**限制**：計數器和參數存在 SRAM，斷電後歸零。LED 的顯示目前沒有用腳本驗證，只能用眼睛看。

### 4.16 `rtl/neuron_top.v`、`host/run_trial.py`：M2 單顆神經元上板比對

這一節是專案的第一個重大里程碑：板子上的神經元和 Python 模型**逐步、逐位元**一致。

**頂層結構**：

```
rx ─▶ uart_rx ─▶ cmd_decoder ─▶ RUN 時：重設 V、I、refrac，開始計步
                                    │
                    lif_core（每個時脈算一步）
                                    │ {spike, V}
                                    ▼
                    記錄記憶體（1024 步，17 bits 一格）──▶ 回覆排程器 ─▶ uart_tx ─▶ tx
```

- **一步一個時脈**：`lif_core` 是組合邏輯（見 4.5）。神經元的狀態存在暫存器裡，每個時脈把「目前狀態 + 輸入」算成「下一步狀態」。27 MHz 下，1000 步約 37 µs。
- **記錄記憶體**：每步寫入 `{spike, V}` 共 17 bits。yosys 把它映射成一個 `DPX9B`（晶片內建的 BSRAM），而不是用 FF 組成，因為 1024 × 17 bits 太大。讀取是同步的：位址先送出，下一個時脈資料才出現（所以排程器有一個等待狀態）。
- **RUN 的語義**：每次 RUN 都先把神經元重設為靜止（V = 0、I = 0、不反應期 = 0），再跑指定步數。這和模型的 `State()` 一致，所以兩邊從相同的初始條件開始比對。
- **回覆排程器**：一次只處理一個請求。`READ_RECORD` 的回覆是串流送出的：每個取樣 3 bytes（V 低位元組、V 高位元組、spike），checksum 在送出的同時累加。

**模擬（`sim/tb_neuron_top.v`）**：
- `host/gen_neuron_vectors.py` 用 Python 模型算出期望的回覆。情境包括：參數設定、輸入 +0.1 跑 40 步、分兩次讀回、再以 −0.1 跑 10 步（測試重設，以及負電位與算術位移）。
- 測試台把每個封包當作序列位元送入，等待該封包的回覆，逐 byte 比對。結果：6 個封包、162 個回覆 bytes **全部一致**。
- 變異測試：把記錄改成寫入前一步的 V，測試失敗（56 處不一致）。
- **這個測試抓到一個真實的設計缺陷**：第一版測試台一次送出所有封包，第二次 RUN 在第一次回覆還在傳送時就開始，覆寫了記錄記憶體，回覆的第 15 byte 之後全部錯誤。修正方式是 4.15 提到的 `busy` 拒絕機制，測試台也改成一次送一個封包、等回覆再送下一個（和 host 的做法一致）。

**板上比對（`host/run_trial.py`）**：
1. WRITE_PARAM：設定 θ = 2.0、V_rest = −0.25、k_m = 4、k_s = 3、refrac = 2，再用 READ_STATUS 確認參數已寫入。
2. 對 20 個輸入電流（−0.1 到 0.375，步長 0.025），每個：RUN 1000 步，然後 READ_RECORD 分 32 步一批讀回（每批約 100 bytes）。
3. 逐步比對 V 與 spike 和模型的 `step()` 結果。
4. 結果：**20,000 個採樣點，0 個不一致，0 次讀取失敗**，板上 err 計數器為 0。
- 發放率：輸入 0.025 時 43 次，之後隨輸入增加，約在 0.25 之後飽和在 332/1000 左右。飽和值的理論上限是 1000/3 ≈ 333，因為 refrac = 2 代表發放後有 2 步不反應，加上發放那一步，每 3 步最多發放一次。
- 圖表（`host/plot_trial.py` 產生）：`docs/m2_trace_board_vs_model.png`（前 100 步的膜電位與 spike 比對）與 `docs/m2_fi_board.png`（20 點的 f-I 曲線，板上與模型疊合）。

**板上的邊界測試**（手動送出，不在 run_trial 裡）：
- READ_RECORD 超出上一次 RUN 的範圍、RUN 步數為 0、RUN 步數為 1025、以及 READ 超出 1 步的紀錄：四個都被拒絕、沒有回覆，err 計數從 0 增加到 4。

**三組參數**（`host/run_trial.py`，每組 20 個輸入 × 1000 步，數值為實際單位，括號內是 Q8.8 raw）：

| 組 | 參數 | 測試重點 | 結果 |
|---|---|---|---|
| A | θ = 2.0（512），V_rest = −0.25（−64），V_reset = 0，k_m = 4，k_s = 3，refrac = 2 | 典型值：有發放、有不反應期、輸入為負時 V 進入負值 | 20,000 個採樣點，0 不一致 |
| B | θ = 0.5（128），V_rest = 0.25（64），V_reset = −0.5（−128），k_m = 0，k_s = 0，refrac = 0 | 位移為 0（值不衰減）；低於閾值不發放，超過閾值後每一步都發放 | 20,000 個採樣點，0 不一致 |
| C | θ = 2.0（512），V_rest = 0，V_reset = −0.5（−128），k_m = 15，k_s = 15，refrac = 7 | 位移為最大值（15）；refrac 最大；負輸入時 V 飽和在 −32768（即 −128.0） | 20,000 個採樣點，0 不一致 |

- 三組都是「寫入參數 → READ_STATUS 確認 → 20 次 RUN → 讀回 → 逐步比對」。掃描期間板上 err 計數器沒有增加。
- 組 B 的 k = 0 讓 `>>> 0` 與 `-(i >>> 0)` 都在硬體上跑過（見 4.5 的 18-bit 中間值）。組 C 的飽和路徑在板上也跑過。

**完整掃描**（`host/sweep.py`，結果見 README 的 Parameter sweep）：
- 格點：k_m（0–15）× k_s（0–15）× refrac（0–7）共 2048 組，θ、V_reset、V_rest 固定。隨機：200 組，θ、V_reset、V_rest、移位與 refrac 都隨機。
- 每組 3 個輸入 × 300 步，逐步比對。合計 2,023,200 個採樣點，**0 不一致，0 次讀取失敗，err 計數器沒有變化**。
- 這次掃描的目的是覆蓋所有移位與 refrac 的合法值。有 24 組格點與 5 組隨機沒有發放，它們也被比對，確認靜默的神經元也與模型一致。
- 整個格點掃描約 25 分鐘（每組約 0.7 秒）。

**限制**：
- 格點掃描固定了 θ、V_reset、V_rest，這三個值只由隨機掃描覆蓋。
- 每次只讀 32 步。整段 1000 步的讀回量是 3 KB，在 115200 baud 下約 0.3 秒，已足夠。
- 還沒做：README 第一節（M2 驗收的文件項目）與 30 秒上板錄影。

### 4.17 `model/network.py`、`rtl/network.v`：M3 網路（模擬，N = 16、64、256）

M3 的目標是 256 顆神經元、有突觸連線的網路。這一節描述網路核心。N = 16、64、256 在模擬中都與模型逐位元一致。把網路接上 UART 命令的完整設計見 4.18，那裡有板上的結果。

**模型規則**（`model/network.py`，決定記在 D-006、D-008、D-009）：
- 所有神經元共用一組參數（之後才會有每顆神經元各自的參數）。
- 第 t 步的發放，在第 t+1 步才進入突觸輸入（延遲一步）。
- 突觸輸入：`syn_in_i = sat( Σ_j (W[j][i] << w_shift)·s_j[t−1] + ext_i )`。**來源的貢獻精確相加，外部輸入加進這個和之後，整個和只飽和一次**。
- 為什麼不像 4.5 的單顆神經元那樣逐次飽和：硬體用事件驅動方式處理發放，發放者的順序是依事件到達的時間，不是神經元編號。逐次飽和會讓結果依順序而變，精確求和再飽和一次則與順序無關。模型測試 `test_order_of_sources_does_not_matter` 會檢查這一點。
- 權重是 8-bit 有號整數，`w_shift = 2`（全域常數，D-009）。

**記憶體組織**（為什麼長成這樣）：
- 只有一顆 `lif_core`，N 顆神經元輪流用它。一步要算 N 次。
- 狀態 `smem`（每顆的 V、I、不反應期計數，共 35 bit）、外部輸入 `emem`、突觸累加器 `amem`、權重 `wmem`（N × N，8 bit）、發放旗標 `spk`。
- FPGA 的區塊記憶體（BSRAM）每個埠一次只能讀或寫一個位址，而且讀取是同步的：位址送進去，資料要等下一個時脈才出來。所以每塊記憶體只設一個寫埠與一個讀埠，讀取位址提前一拍送出，下一拍才用資料。這就是階段 A、B 要做成流水線的原因。
- 累加器有兩塊（`amem[0..N−1]` 與 `amem[N..2N−1]`）。一步內讀的是「本步的輸入」，寫的是「下一步的輸入」，兩者不能共用同一塊。用 `par` 旗標交替：本步讀 `cur`、寫 `nxt`，下一步對調。不需要搬移資料。
- 舊版用陣列加上一次讀寫很多元素的寫法。綜合器只能把它做成正反器與多工器，N = 256 時約 45,000 cells，遠超過 GW2AR-18 的邏輯資源（見資源）。現在改成單寫埠單讀埠，綜合器會把它們放進 BSRAM。

**硬體的三個階段**（`rtl/network.v`，一步的流程）：
- **A（神經元更新，流水線）**：每個時脈處理一顆 k。第一拍送出讀取（`smem[k]`、`emem[k]`、`amem[cur][k]`）。下一拍：`syn_in = sat16(acc + ext)`，交給 `lif_core`（同一個組合電路，4.5）；新狀態寫回 `smem[k]`；發放寫入 `spk[k]`；`(V, spike)` 送到輸出 `rec_*`，測試台逐筆比對。同一拍把 `amem[nxt][k]` 清為 0。
- **B（突觸，事件驅動）**：對每一顆本步發放的來源 k，對所有目標 i 做 `amem[nxt][i] += W[k][i] << 2`。流水線：一拍送出讀取（`amem[nxt][i]`、`wmem[k][i]`），下一拍做加法寫回。沒有發放的來源只佔一個週期。
- **結束**：`par` 翻轉，步數加一。

**為什麼流水線不會讀到舊值**：B 階段連續兩次送出的讀取，目標 i 一定不同（同一來源內 i 逐一遞增，跨來源時 i 從 N−1 回到 0）。所以前一次寫入還沒完成時，下一次讀取不會碰到同一個位址。A 階段清零的 `nxt`，是上一步已經讀完的那一塊，而 A 在 B 之前完成，所以清零不會影響本步的讀取。

**驗證**（`sim/tb_network.v`）：
- 隨機的 E/I 網路（80% 興奮、20% 抑制，連線機率 min(0.5, 8/N)，每顆平均約 8 個輸入；`host/gen_net_vectors.py`），外部驅動固定，從靜止跑 200 步。
- 逐筆比對，全部與模型一致：

| N | 紀錄數（200 步 × N） | 結果 |
|---|---|---|
| 16 | 3,200 | PASS |
| 64 | 12,800 | PASS |
| 256 | 51,200 | PASS |

- 變異測試：四個故意做壞的版本都報 FAIL：W_SHIFT 改為 3、少算最後一個目標、突觸輸入不傳遞、寫到錯誤的累加器緩衝。
- N = 256 的模擬跑了約 147 ms 的模擬時間，所以測試台的逾時上限從 50 ms 改為 2 s。這只影響模擬，不影響硬體。
- 測試過程中的錯誤：
  1. 第一次的 W_SHIFT 變異沒有生效，因為測試台實例化時用 `.W_SHIFT(2)` 覆寫了參數。修正：變異時也改測試台。
  2. 「同一步延遲」的變異在舊設計與新設計中都等價於原設計，所以它「通過」不是測試的錯。改用「寫到錯誤緩衝」的變異代替。

**資源**（yosys `synth_gowin`，用 `chparam` 設定 N）：

| 版本 | N = 16 | N = 64 | N = 256 |
|---|---|---|---|
| 舊版（陣列） | 約 8,500 cells | — | 約 45,400 cells，記憶體變成正反器 |
| 目前（單埠 BSRAM 風格） | 1,382 cells | 1,343 cells | 1,457 cells；區塊記憶體 32 DPB + 2 SDPX9B + 1 DPX9B |

- N = 256 的 32 個 DPB 大致就是權重記憶體（65,536 × 8 bit = 512 Kbit）。
- N = 16 的小記憶體仍用查找表記憶體（RAM16SDP4），這是綜合器對小陣列的選擇，不是錯誤。
- **place-and-route（nextpnr-himbaechel，GW2AR-18）**：用一個測試外殼（`build/pnr/net_pnr_top.v`，不是板上設計）包住 N = 256 的網路。外殼把網路的輸入接到計數器、輸出縮成一個腳位，因為整個網路的腳位數超過晶片的 I/O。結果：
  - 區塊記憶體 35 / 46（76%）
  - LUT4 785 / 20,736（3%），DFF 392 / 15,552（2%），IOB 2 / 384
  - 最高頻率 47.4 MHz，目標 27 MHz，**通過**
  - 布線成功，`gowin_pack` 產生 `build/pnr/net_pnr.fs`。這個檔案只用來確認流程，還沒有燒上板子。
- 外殼的輸入來自計數器，yosys 因此能化簡掉一部分邏輯，所以它的綜合 cells（1,014）比單獨網路（1,457）少。PnR 的數字比較接近真實，但板上加入指令解碼器與 UART 後，邏輯與 BSRAM 用量還會增加，要再量一次。

**限制與還沒做**：
- 權重與輸入現在由 4.18 的 `WRITE_WEIGHTS`、`SET_INPUT` 載入（模擬時是測試台直接寫入）。還沒做：每顆神經元各自的參數；LFSR 雜訊。完整流程見 4.18。
- 隨機網路的發放率很高：N = 16 時每顆 38 到 66 次（200 步），最高的 66 已接近不反應期的上限（refrac = 2，約每 3 步一次）。做 E/I 實驗前要降低外部輸入或權重，否則結果會貼近飽和。
- N = 256 時有神經元完全不發放（最少 0 次）。

### 4.18 `rtl/network_top.v`：完整網路設計（UART 命令、權重載入、讀回）

4.17 的網路核心只能在模擬裡跑。這一節是把它接上 UART 的完整設計，也就是板上要燒的版本。它的資料流是：

```
uart_rx → cmd_decoder → 複製 FSM → network（wmem、emem 在這裡載入）
              │                         │
              │                  執行控制、每顆神經元的記憶體
              │                         │
              └──→ 回覆排程器 ←─────────┘ → uart_tx
```

**協定擴充**（`host/protocol.py`，D-011）：

| 命令 | 代碼 | 內容 | 回覆 |
|---|---|---|---|
| WRITE_WEIGHTS | 0x02 | 起始位置（2 bytes），然後是權重（每個 1 byte，有號） | 無 |
| SET_INPUT | 0x03 | 起始神經元（2 bytes），然後是 Q8.8 輸入（每個 2 bytes） | 無 |
| READ_STATUS | 0x06 | 無 | 0x86：ok、err、已完成步數（2 bytes），共 4 bytes |
| READ_COUNTS | 0x07 | 起始（2 bytes）、數量（1 byte，1..64） | 0x87：每顆神經元的發放次數（2 bytes） |
| READ_SNAPSHOT | 0x08 | 同上 | 0x88：每顆神經元最後一步的 V 與 spike（3 bytes） |
| READ_TRACE | 0x09 | 起始步（2 bytes）、步數（1 byte，1..7） | 0x89：每步 N/8 bytes 的 spike（見 4.20） |

RUN 的格式不變，但網路版會忽略它的輸入欄位，因為輸入改由 SET_INPUT 逐顆設定。

**網路版的參數限制**：`network_top` 要求 N 是 2 的次方且 N ≥ 16。READ_TRACE 每個封包 7 步的上限，只在 N ≤ 256 時成立（回覆長度不能超過 255 bytes）。`host/gen_net_top_vectors.py` 要求 7 ≤ T ≤ 1024。

**為什麼 decoder 要能緩衝 255 bytes**：WRITE_WEIGHTS 一次最多送 253 個權重。decoder 原本只存 16 bytes。現在整個 payload 都存進緩衝，checksum 通過後才寫入網路。checksum 壞掉的封包不會改動任何權重，這和 4.12 的原則一樣。

**為什麼讀回的是「計數 + 快照」，不是逐步紀錄**：如果每一步每顆神經元都存 (V, spike)，N = 256、1024 步要 256 × 1024 × 17 bit ≈ 4.4 Mbit，遠超過 GW2AR-18 的區塊記憶體（約 828 Kbit）。現在的做法只需要每顆神經元一個計數器（16 bit）與一個快照（17 bit），共 N × 33 bit，N = 256 時約 8.4 Kbit。代價是看不到中間步的 V，只能看到發放次數與最後一步的 V。中間步的 spike 另由 READ_TRACE 讀回（4.20）。

**複製 FSM**：權重一拍寫一個。輸入每個值要兩拍，先讀低位元組，再讀高位元組，組成 16-bit 後寫入。它的讀取位址直接從 decoder 的緩衝來，寫入的同時把位址與資料各打一拍，和 `network.v` 的寫埠時序一致。一個封包最多 253 bytes，複製最多約 260 個時脈；兩個位元組之間至少有 2349 個時脈（115200 baud），所以複製一定會在下一個封包到來前完成。

**執行控制與計數器**：收到 RUN 後，先用 N 個時脈把計數器清成 0，再啟動網路。網路每產生一筆紀錄，就更新兩個記憶體：
- 計數器：`cnt[k] += spike`。這是「讀出 → 加 → 寫回」的運算，需要兩拍。之所以不會出錯，是因為連續的紀錄來自不同的神經元（k 逐一遞增），同一顆神經元的兩次更新至少相隔 N 拍。
- 快照：`snap[k] = {spike, V}`，直接覆寫。跑完一次 RUN 之後，快照就是最後一步的值。

`busy` 的規則：`busy` 為高時，所有命令都被拒絕並計入 err，包括 WRITE_PARAM、READ_RECORD 與 READ_TRACE。`busy` = 回覆正在傳送 或 複製進行中 或 網路執行中。這保證執行中不會改參數、權重或輸入。

**回覆**：STATUS 是 8 bytes（一份在收到請求時拍下的快照）。COUNTS 與 SNAPSHOT 是「標頭 + 每顆神經元一筆 + checksum」。記憶體用暫存器位址讀取，每筆等一拍。

**驗證**（`sim/tb_network_top.v`，位元組層級，從 rx 腳位送 bits、從 tx 腳位收 bits）：
- `host/gen_net_top_vectors.py` 產生完整的一次使用流程：WRITE_PARAM、權重分塊、一次超出範圍的 WRITE_WEIGHTS、一個 checksum 錯誤的封包、SET_INPUT、STATUS、RUN、STATUS、COUNTS、SNAPSHOT，最後是一次超出範圍的 READ 與 STATUS。壞封包必須計入 err 且不改變任何狀態。
- 預期的回覆來自 `model/network.py`。
- N = 16：14 個封包、112 bytes 回覆，全部一致，最後 err = 3（三個壞封包）。
- N = 64：52 個封包、352 bytes 回覆，全部一致。
- N = 256：682 個封包、70,168 bytes 輸入、1,892 bytes 回覆，全部一致（含 READ_TRACE）。加入軌跡之前的舊執行是 675 個封包、70,119 bytes、1,336 bytes，最後 ok = 672、err = 3，模擬約 441 秒。加入軌跡之後，最後的計數是 ok = 675、err = 7（多了 3 個軌跡讀取與 4 個故意錯誤的軌跡命令）。
- **板上（`host/board_network_test.py`，`/dev/ttyUSB1`）**：同一組 682 個封包，經 UART 送進 Tang Nano 20K。因為橋接晶片在連續超過約 64 bytes 時會丟資料，封包以 16 bytes 分段、按線速節流送出；有回覆的封包讀完整個回覆才送下一個。**1,892 bytes 回覆全部與模型一致，PASS，耗時 44.4 秒**（2026-11-06 重跑，log 見 `results/board_network_test_2026-11-06.log`）（軌跡版 bitstream，燒錄後的新板）。RUN 沒有回覆，所以 RUN 之後要等一段時間才送下一個命令。等待時間由步數算出：每步最壞情況是 N + N² + 2N 個時脈，換算成 27 MHz、乘 1.2 再加 0.1 秒。原本固定的 2 秒，對 N = 256、1024 步、每顆神經元都發放的情況只有約 2.5 秒需要，所以不夠。腳本失敗時結束碼為 1。這次結果確認的是「命令、權重與輸入載入、執行、讀回」整條路徑在硬體上與模型一致；它不是逐步的軌跡比對，也不包含 E/I 實驗。
- **busy 拒絕**（`sim/tb_decoder_busy.v`，新增）：之前的 `tb_cmd_decoder` 把 busy 固定為 0，其他測試台都等到閒置才送命令，所以「忙碌時拒絕」沒有被直接測過。新的測試台在 busy 為高時送每一種命令，檢查它們都被拒絕、計入 err、沒有回覆，也沒有改動任何狀態。結果：PASS（9 種命令都被拒絕；忙碌解除後 WRITE_PARAM 與 RUN 被接受）。另外故意讓 READ_STATUS 不檢查 busy，測試台會 FAIL，證明它抓得到這類錯誤。
- 三個變異測試（都應該 FAIL，結果都是 FAIL）：
  - 兩個輸入位元組對調：第 19 個回覆位元組不符。
  - 範圍檢查差一（`NET_CELLS + 1`）：壞的 WRITE_WEIGHTS 被接受，後續的 err 與 ok 計數錯誤。
  - 計數器的讀-改-寫時序錯誤（用 `rec_spk` 代替延遲一拍的 `rec_spk_d`）：計數錯誤。

**資源**（`make TOP=network_top`，nextpnr-himbaechel，GW2AR-18；這是加入軌跡讀回之前的版本，新數字見 4.20）：
- LUT4 2,355 / 20,736（11%），DFF 1,264 / 15,552（8%），區塊記憶體 37 / 46（80%），RAM16SDP4 66 / 648。
- 最高頻率 42.9 MHz（布線後的報告），目標 27 MHz，通過。nextpnr 把整個設計的時脈命名為 `u_dec.clk`，這只是網路名稱，設計裡只有一個時脈。
- 產生 `fpga/build/network_top.fs`，已用 `make flash TOP=network_top` 燒進 SRAM（揮發性，斷電消失）。

**還沒確認的事**：
- yosys 對 `wmem`（8-bit，65536 格，映射成 32 個 DPB）發出 12 條 `brams_map.v` 警告：`PORT_A_WR_DATA` 的 `[7:0]` 等範圍超出界線，填補為 undef。從映射的實例看，這些是 1-bit 寬度的 BSRAM 條塊（`BIT_WIDTH_0 = 1`）的填補位元，應該不影響結果，但我**還沒有用網表模擬證明**。原因已查清：安裝的 Gowin 區塊記憶體模擬模型（`DPB`、`SDPX9B`、`DPX9B`，在 `cells_xtra_gw2a.v`）只有埠宣告，沒有行為內容，所以網表模擬一定會讀到 `x`。這個工具鏈無法做網表模擬。2026-11-04 決定以上板結果作為功能驗證，不再追這件事。
- READ_RECORD 在網路版沒有回覆，但 decoder 仍會把它計為 ok。host 不應該送這個命令。
- 協定（D-007、D-011）已由作者審閱。
- 板上只跑了一次完整流程（N = 256，見下）。之後的 E/I 條件也上了板，並加入了逐步 spike 軌跡的比對（4.20）。V 的逐步軌跡還沒有板上比對。

### 4.19 E/I 擾動實驗（模型掃描與上板驗證，N = 256）

問題：興奮與抑制的比例（E/I）改變時，網路的平均發放率怎麼變？這是 `CLAUDE.md` 列的第一個實驗目標。

**先決定網路的設定**（`host/ei_sweep.py`）：
- N = 256，每顆神經元平均 8 個輸入（連線機率 8/N）。興奮來源的權重是 [0, w_max] 的隨機整數，抑制來源是負的。
- 外部輸入：每顆神經元一個常數，0 到 e_max（Q8.8 raw）。
- 一開始用 `w_max = 60`（`gen_net_top_vectors.py` 的值）時，網路不是沉默就是飽和，發放率 0.33 = 不反應期上限。原因：權重 60 左移 2 位是 240 raw，約 0.94；單一輸入幾乎就能把電位推到閾值 1.5。活動由遞迴連線主導，外部輸入的影響幾乎消失。
- 把 `w_max` 降到 10（每個輸入約 0.16）後，網路進入不飽和的區間，f_inh 的效果才看得清楚。所以實驗採用 `w_max = 10`、`e_max = 30`。`w_max` 是生成網路時的參數，不是 RTL 的參數，也不是生理校正的結果。

**結果**（`host/ei_experiment.py`，每個 f_inh 用 3 個隨機網路，各跑 600 步，前 100 步不計）：

| f_inh | 平均發放率 | 範圍（3 網路） | 沉默神經元比例 |
|---|---|---|---|
| 0.0 | 0.316 | 0.313–0.319 | 0.00 |
| 0.1 | 0.291 | 0.284–0.294 | 0.01 |
| 0.2 | 0.249 | 0.242–0.253 | 0.02 |
| 0.3 | 0.210 | 0.201–0.217 | 0.07 |
| 0.4 | 0.175 | 0.171–0.181 | 0.13 |
| 0.5 | 0.149 | 0.146–0.154 | 0.19 |
| 0.6 | 0.123 | 0.120–0.130 | 0.26 |

圖：`docs/ei_rate_vs_finh.png`（`host/plot_ei.py` 產生）。

**解讀**：抑制比例增加，發放率單調下降，沉默神經元增加。f_inh = 0 時已接近不反應期上限（0.316 對 0.333），所以有意義的範圍大約是 0.2 到 0.5。發放率是無單位的（每步每顆神經元的發放比例），不是生理的 Hz，不能直接和生物資料比。

**上板驗證**（`host/ei_board_test.py`）：f_inh = 0.2 與 0.5 兩個條件。所有回覆（256 顆神經元的計數、最後一步快照，以及前 512 步的 spike 軌跡）都與 `model/network.py` 的**完整模型**逐位元一致。這裡的參考是完整模型，不是掃描用的稀疏版，所以掃描的算術也一起被檢查。

2026-11-04 加入軌跡讀回後重跑：f_inh = 0.2 與 0.5（w_inh = 1）的模型發放率，板上腳本 `ei_board_test.py` 以全部 600 步計算，為 **0.246** 與 **0.138**；扣掉前 100 步後為 0.250 與 0.139。先前這一節寫的 0.238 與 0.144（當時 662 個封包）也是板上腳本以全部 600 步計算的數字，但用的是另一組網路。原因是 ext 的抽取方式不同：板上腳本的 W 由 `ei_full_sweep.build` 產生，ext 用 `random.Random(seed*1000 + e_max)` 抽取；`ei_sweep.py` 與 `ei_experiment.py` 在生成 W 之後從同一個亂數產生器抽取 ext，順序不同。當 w_inh = 1 時 W 相同，只有 ext 不同，所以發放率不同。目前的板上執行用的是 `ei_full_sweep.build` 的網路，因此是 0.246 與 0.138。這個解釋是從程式碼推論出來的。我用目前的生成器重現了 0.246 與 0.138，但沒有用舊的 ext 抽取方式重跑 662 個封包的執行，所以舊的網路沒有被重現。網路生成、比對對象與逐位元比對的結果都沒有受影響。比較數字時要注意：`ei_sweep.measure` 與 `ei_experiment.py` 的數字扣掉前 100 步，板上腳本的數字是全部 600 步。

**完整掃描**（`host/ei_full_sweep.py`，`host/ei_full_summary.py`）：f_inh 從 0 到 0.6（每 0.1）、w_inh 0.5 / 1.0 / 1.5 / 2.0、w_max 10 / 20、e_max 10 / 30 / 60，每組 10 個隨機網路（seed 20261104 起，共 10 個），共 1,680 次執行。`w_inh` 是抑制權重相對於興奮權重的倍率；`w_max` 是興奮權重的上限。（2026-11-04 由 3 個網路擴大到 10 個，前 3 個網路的結果與舊版逐位元相同，表示生成器沒有改變。）

- 24 組（w_max × w_inh × e_max）的平均發放率，在 f_inh 增加時全部單調不增（容許誤差 0.005）。
- 抑制權重的效果很大。以 w_max = 10、e_max = 30、f_inh = 0.6 為例，w_inh = 0.5 時發放率 0.160，w_inh = 2.0 時 0.085。
- 沉默比例隨抑制增強而增加。同一組（w_inh = 2.0、f_inh = 0.6）有 44% 的神經元沉默。

- 沒有掃連線機率、每顆神經元不同的參數，也沒有加入 LFSR 雜訊。

- 沒有加入 LFSR 雜訊，也沒有每顆神經元各自的參數。

### 4.20 逐步 spike 軌跡（READ_TRACE）

**問題**：4.18 只能讀回每顆神經元的發放次數與最後一步的快照。要和模型逐步比對，需要每一步的結果。

**為什麼不能全部存**：每一步每顆神經元存 (V, spike) 需要 17 bit。N = 256 時一步就是 4,352 bit，剩下的區塊記憶體只夠存約 40 步。只存 spike，每顆神經元 1 bit，N = 256 時一步是 256 bit，512 步約 128 Kbit，還放得下。所以這裡的取捨是：**只存 spike，不存 V**；存最多 512 步。V 的逐步軌跡仍然只能用 RUN k 步再讀快照的方式取得，網路每次 RUN 都從靜止開始（做得到，但慢，目前沒做）。

**怎麼寫進去**（`rtl/network_top.v`）：網路每個時脈最多送出一筆紀錄，順序是 k = 0、1、…、N−1。
- 用一個 8 bit 的移位暫存器 `tsh` 收集 spike：每筆紀錄把自己的 spike 從最高位移進去。移了 8 次之後，最早的那顆神經元在最低位，所以 bit j 就是神經元 8b+j。
- 每當 k 的低 3 位是 7（湊滿一個 byte），就把 `{spike, tsh[7:1]}` 寫進 `tmem[{步, k 的高位}]`。
- 寫入的步位址用 `steps_done`。它在這一步的最後一筆紀錄的同一個時脈還是舊值，正好是這一步的編號，所以不需要另外的計數器。寫入條件是 `steps_done < 512`。

**記憶體的形狀**：8 bit 寬，深度 512 × N/8。選 8 bit 寬而不是 256 bit 寬，是因為綜合器比較容易映射成區塊記憶體，也不需要 256 個正反器當暫存列。N = 256 時是 16,384 × 8 bit，約 128 Kbit。

**怎麼讀出**（命令 0x09）：
- 請求：起始步（2 bytes）、步數（1 byte，1 到 7）。
- 回覆：每步 N/8 bytes，第 b 個 byte 的第 j 個 bit 是神經元 8b+j。7 步 × 32 bytes = 224 bytes，放得進一個回覆（長度欄位只有 1 byte，上限 255）。
- 合法範圍：起始 + 步數 ≤ min(run_len, 512)。`run_len` 是 decoder 記住的最近一次 RUN 的步數。超出範圍的請求計入 err，不回覆。這樣就不會讀到上一次較長的 RUN 留下的舊資料。
- 讀記憶體的時序：位址改變後要等一拍記憶體才會出現資料，所以每送一個 byte 之前有一個等待狀態（Q_TWAIT）。每送完一步，步位址加 1。
- host 端：`pack_read_trace` 拒絕「起始 + 數量 > 512」，`unpack_trace` 拒絕 n ≤ 0（`host/protocol.py`）。

**為什麼是 7 步一個請求**：一個回覆最多 255 bytes，N = 256 時一步 32 bytes，所以 7 步是上限。對 N = 16 也適用，因為每步只有 2 bytes。

**資源**（`make TOP=network_top`，加入軌跡讀回之後）：
- BSRAM 45 / 46（98%，45/46 = 97.8%）。原來的 37 塊加上軌跡的 8 塊。只剩 1 塊，之後要加功能前要先算空間。
- LUT4 2,536 / 20,736（12%），DFF 1,315 / 15,552（8%）。
- 最高頻率（布線後，關鍵路徑報告）38.75 MHz，目標 27 MHz，通過。先前寫的 41.38 MHz 是布局後的估計，不是最終結果（2026-11-04 更正）。
- yosys 對 8 bit 記憶體發出 `brams_map.v` 的範圍警告，和 4.18 提到的 `wmem` 警告是同一類。這些警告還沒有用網表模擬證明，板上結果是目前的功能證據。

**驗證**：
- 模擬（`sim/tb_network_top.v`，位元組層級）：
  - N = 16、T = 200：21 個封包、158 bytes，PASS。
  - N = 16、T = 600：PASS。這一組測的是 512 步的上限，差一錯誤會被抓到：起始 509 步、數 3 步（剛好到 512）要接受，起始 510 步、數 3 步（到 513）要拒絕。
  - N = 64、T = 200：59 個封包、500 bytes，PASS。
  - N = 256、T = 200：682 個封包、1,892 bytes，PASS。
- 變異測試（都應該 FAIL，結果都是 FAIL）：
  - bit 順序對調：回覆第 113 個 byte 不符。
  - 步位址加 1：第 107 個 byte 不符。
  - 上限從 512 改成 513：壞的讀取被接受，回覆格式錯，第 151 個 byte 不符。
  - 數量上限從 7 改成 8：同上，第 151 個 byte 不符。
- 板上（`host/ei_board_test.py`，f_inh = 0.2、0.5、0.5 的 w_inh = 2.0 與 0.5、0.3 的 w_inh = 1.5 與 w_max = 20）：五個條件，每個 745 個封包（計數、快照、前 512 步的軌跡），全部與 `run_network` 逐位元一致。
- 板上的 N = 256 命令流程（`host/board_network_test.py`）：682 個封包、1,892 bytes，PASS。第一次跑 FAIL，三個狀態回覆不符。原因不是設計錯誤：前面五個 E/I 條件之後，板上的 ok/err 計數和步數沒有歸零，而這個測試假設剛燒完的板子。重新燒錄後再跑即 PASS。之後跑這個測試前要先重燒。板上目前沒有 reset 命令，計數器會跨 session 保留，所以這個限制還在。

**限制**：
- 只有 spike，沒有 V 的逐步軌跡。
- 最多 512 步。E/I 的 600 步實驗只比對前 512 步的 spike；後面 88 步只有計數與快照。
- `neuron_top` 與 `cmd_test` 的版本也接受 0x09，但沒有回覆，decoder 仍計為 ok（和 READ_RECORD 在網路版的情況相同）。

### 4.21 飽和覆蓋：`host/clamp_census.py`、`host/saturation_board_test.py`（2026-11-06）

**白話說明。** 定點數加法超出 [−32768, 32767] 就夾到邊界（飽和），而不是繞回。單顆神經元每一步有四次這樣的加法：

| 位置 | 算什麼 | 能不能飽和 |
|---|---|---|
| `i1` | 電流衰減 `I − (I ≫ k_s)` | 不能。結果一定在 `I` 與 0 之間 |
| `i2` | 把輸入加進電流 | 能（正、負兩個方向） |
| `v1` | 漏電 `V + ((V_rest − V) ≫ k_m)` | 不能。結果一定在 `V` 與 `V_rest` 之間 |
| `v2` | 把電流加進膜電位 | 能（正、負兩個方向） |

`v2` 的上限比較特別。夾到上限時的值是 32767，而 θ 最大也是 32767，所以一定 ≥ θ。結果只有兩種：神經元發放（膜電位重設為 V_reset），或者在不反應期（膜電位被丟棄、重設為 V_reset）。兩種情況下，夾不夾結果都一樣，所以這個上限**不影響輸出**，不需要專門測。

**為什麼要測。** 論文之前說「板上沒有碰到飽和」，這個說法是錯的。用模型追蹤後發現：參數組 C（k_m = k_s = 15）在板上 20 個輸入裡有 14 個碰到飽和，而板上每一步的結果都與模型一致。所以論文必須改寫，並補上一個專門的測試。

**怎麼數。** `host/clamp_census.py` 有一份追蹤版的模型：和 `model/fixed.py` 的 `step()` 一樣，只是每次 `sat()` 被夾住時記一筆（位置與方向）。這份追蹤版每一步都會用 `assert` 檢查，狀態必須和 `fixed.step` 完全相同，否則腳本會失敗。它統計了四類執行：

- `host/run_trial.py` 的參數組 C 的 20 個輸入（每個 1000 步）：`i2+` 4,701 次，`v2−` 3,705 次，14 個輸入碰到飽和。參數組 A、B 完全沒有碰到。
- `host/sweep.py` 的網格與隨機掃描（每組 3 個輸入、300 步）：`v2−` 在網格的 2,048 組中有 1,400 組、隨機的 200 組中有 130 組發生。`i2` 沒有碰到。
- 飽和測試的參數組（見下）。
- 單顆神經元的搜尋：用極端輸入確認哪些位置能到達（結果：`i2+` 與 `i2−`、`v2−`）。

**上板測試。** `host/saturation_board_test.py` 用四組參數。S1、S2 的 θ = 512、k_m = k_s = 15、V_rest = 0，S2 的 V_reset = −128、refrac = 7。S3 的 θ = −32768（最小值），k_m = k_s = 15，這時下鉗位會決定是否發放。S4 的 θ = −128、V_reset = −256、k_m = 4、k_s = 3、refrac = 2，是負門檻搭配一般位移。五個常數輸入是 −128.0、−15.625、−3.90625、+15.625、+127.99609375，也就是原始值 −32768、−4000、−1000、+4000、+32767，每個跑 100 步。它沿用 `run_trial.py` 的協定和比對方式（每一步的 V 與 spike 與模型比對）。結果：四組共 2,000 個樣本、0 個不一致。S1、S2 碰到 `i2+`、`i2−`、`v2−`。S3 只碰到 `i2+`、`i2−`，因為發放後膜電位重設為 0，`v2` 不會再被推到下限。S4 碰到 `i2−`、`v2−` 與 `i2+`。

**讀不到 I。** 板子只回傳 V 與 spike，不回傳 I。所以 `I` 的飽和是間接看到的：`I` 被夾住之後，`V` 的變化會不一樣，而這個差異被每一步的比對抓到。

**負門檻。** 上鉗位的論證只需要 θ ≤ 32767，對所有 16 位元的門檻都成立，正負都一樣。下鉗位則不同：未夾住的值若小於 −32768，夾住後變成 −32768。只有當 θ = −32768 時，夾住後的 −32768 會滿足 `V ≥ θ`，而未夾住的值不會，所以只有這個門檻會因為下鉗位而改變發放。S3 就是測這個情況，板上每一步都與模型一致。模型以飽和後的算術定義這個行為，所以它是規格的一部分，不是漏洞。

**還沒涵蓋的。** 網路內部的飽和沒有計數。網路的膜電位只在最後一步比對（見論文限制一節）。

**怎麼重現。**

```bash
python host/clamp_census.py > results/clamp_census.log
```

（上板）先燒錄 `neuron_top`，再執行：

```bash
python3 host/saturation_board_test.py /dev/ttyUSB1
```

燒錄與測試的 log 存於 `results/flash_neuron_top_2026-11-06.log` 與 `results/saturation_board_test_2026-11-06.log`。

### 4.22 第二輪審查的補強：`host/protocol_robustness_board_test.py`、`host/negative_control.py`、`host/sum_magnitude.py`（2026-11-06）

**白話說明。** 第二輪審查指出四件事：板上沒有錯誤輸入的測試、比對程式本身沒有被驗證能不能抓錯、網路累加器的位寬只有理論論證、論文沒有列出網路與飽和測試的實際參數。這一節對應的三個腳本各處理一件事。

- **錯誤輸入的板上測試**（`host/protocol_robustness_board_test.py`，`results/protocol_robustness_board_test_2026-11-06.log`）：送四種錯誤，並記錄回覆與錯誤計數的變化。（1）checksum 錯誤：無回覆，錯誤計數 +1。（2）未知命令 0x0A：無回覆，+1。（3）忙碌：送出 `READ_RECORD` 後，在回覆還在傳送時送 `READ_STATUS`，只收到 `READ_RECORD` 的回覆，錯誤計數 +1，證明忙碌時的拒絕規則在板上被實際觸發。（4）截斷的封包 `A5 06 00` 接著一個合法的 `READ_STATUS`：decoder 沒有 time-out，會把合法封包的第一個 byte 當成截斷封包的 checksum，合法封包因此遺失，錯誤計數 +1；之後的合法封包正常回覆。四項都與預測一致。
- **比對程式的負向對照**（`host/negative_control.py`，`results/negative_control_2026-11-06.log`）：拿板上真的回傳的 20 條軌跡，用和板上檢查相同的比較式（`a != b`，逐步比 V 與 spike）。未修改時差異為 0。然後故意注入四種錯誤：翻一個 V 的 bit、移除一個 spike、軌跡平移一步、整條軌跡換成另一個輸入的軌跡。四種都被偵測到。這是比對程式對真實資料的敏感度測試，不是板級突變測試。
- **累加器實際用到的範圍**（`host/sum_magnitude.py`，`results/sum_magnitude.log`）：用模型重建板上使用的網路（同樣的產生器與種子），記錄每一步每顆神經元的未飽和突觸和。命令流的最大值是 1,084，E/I 五個條件的最大值是 378，都遠小於 2^15。也就是說，累加器第 10 位以上在板上只承載符號位元。24 位元寬度是上界的論證，不是板上實測的結果。

**還沒做。** 第 512 步之後的完整狀態讀回、I 的讀回、板級突變測試、非定速 UART 的壓力測試，都需要改 RTL 或新的上板實驗，本輪沒有做。

| 算術位移 | 右移時保留符號的位移 |
| 組合邏輯 | 輸出只依賴目前輸入，沒有記憶 |
| 循序邏輯 | 輸出依賴內部狀態，由時脈驅動更新 |
| LUT / FF | FPGA 的基本單元：查找表（組合）與正反器（記憶） |
| BSRAM | 晶片內建的大塊記憶體 |
| bitstream | 寫入 FPGA 的設定檔，決定晶片的電路 |
| SRAM 燒錄 | 寫入 FPGA 的揮發性記憶體，斷電消失 |
| UART 8N1 | 串列傳輸，8 個資料位元、無同位元、1 個停止位元 |
| 同步器 | 兩級 FF，避免外部訊號造成亞穩態 |
| 握手 | 發送方用 start/busy 確認接收方是否準備好 |
| 封包 / checksum | 資料的框架與錯誤偵測碼 |
| 逐位元比對 | 硬體與模型的每個輸出位元都必須相同 |
| 變異測試 | 故意改壞程式，確認測試會抓到 |

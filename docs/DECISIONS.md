# 設計決定紀錄（DECISIONS）

> 作者已審閱（2026-11-06）。

## D-001 數值格式採用 Q8.8（有號 16-bit）

- **決定：** 膜電位 V 與突觸電流 I 都用有號 Q8.8，其中 raw = 實數 × 256。
- **理由：** 16-bit 能放進 DSP 外的一般邏輯，`>>` 位移即可代替乘法；精度（1/256）足夠看 f-I 曲線形狀。
- **代價：** 小於 1/256 的變化會被量化掉。`(V_rest − V) >> k_m` 在差值小於 2^k_m raw 時為 0，形成死區（f-I 曲線在閾值附近的階梯來源之一）。

## D-002 所有加法飽和，不繞回

- **決定：** 每一次加法後都 clamp 到 [−32768, 32767]，而且是「逐次加法後飽和」（從左到右）。
- **理由：** 繞回會把強烈的興奮輸入變成強烈的抑制，造成難以察覺的行為錯誤。
- **驗證：** `model/test_fixed.py::test_sadd_saturates_after_each_addition` 與兩個 saturation 測試。

## D-003 右移為算術位移（向負無限取整）

- **決定：** `>>` 在 Python 與 RTL（`>>>` 於有號暫存器）都是算術位移。
- **理由：** 邏輯右移會讓負的膜電位在衰減時變成大正數。
- **注意：** 常見錯誤是寫成 `>>`（邏輯）而非 `>>>`（算術），RTL 必須為有號宣告。

## D-004 leak 差值以 17-bit 計算

- **決定：** `V_rest − V` 在位移前以 17-bit 精確計算。
- **理由：** 兩個 16-bit 有號數相減可能需要 17 bit；若先截成 16-bit 會在極端輸入下得到錯誤的 leak。Python 模型自然是精確的，RTL 必須對齊。

## D-005 不反應期語義

- **決定：** 發放後 V 設為 V_reset，計數器設為 `refrac`；之後每步 V 保持 V_reset、計數器遞減，計數器為 0 時才能再次發放。I 照常積分。
- **理由：** 最簡單、最容易逐位元比對。
- **效果：** 最高發放率受 `refrac` 限制，f-I 曲線會出現階梯（見 `docs/fi_curve.png`）。

## D-006 更新順序（同步、下一步生效）

- **決定：** 第 t 步的發放 s[t] 在第 t+1 步才進入突觸電流 I。
- **理由：** 避免同一步內的讀寫競爭，和 RTL 的分時排程一致。Python 網路模型必須用同樣順序（M3 實作時再補）。

## D-007 PC–板子協定

- **決定：** 封包為 `[0xA5][cmd][len][data…][checksum]`，checksum = `(cmd + len + Σdata) mod 256`，多位元組值採 little-endian，Q8.8 為有號 16-bit，權重為有號 8-bit。回應沿用同一格式，cmd 的最高位設為 1。指令代碼見 `host/protocol.py`。
- **理由：** 計畫書指定了封包外型，但沒有指定 checksum 與位元組序。加總式 checksum 在 MCU/FPGA 端只要一個加法器；長度欄位讓接收端不需要結束符號。
- **代價：** 加總式 checksum 抓不到互換位元組或 0 與 256 的組合等錯誤；對 UART 的單位元錯誤可以抓到，但不如 CRC 可靠。目前的傳輸量小，這個風險可以接受。若之後的資料量變大，再改成 CRC-8。
- **注意：** 0xA5 也可能出現在資料中，因此解析器是依長度欄位跳過資料，不是依 0xA5 切分。
- **狀態：** 已審閱（2026-11-06）。

## D-008 網路更新順序與突觸輸入求和（M3）

- **決定：** 第 t 步的每顆神經元，輸入為 `syn_in_i[t] = sat16( Σ_j (W_ji << w_shift)·s_j[t−1] + ext_i )`。也就是先把本步所有發放的前突觸貢獻精確相加（寬暫存器），再把外部輸入加進這個精確的和，最後只飽和一次。之後所有神經元以 `syn_in` 同時更新，產生 `s[t]`。
- **理由：** 硬體用事件驅動的方式處理發放，發放者的順序是依事件到達，不是依神經元編號。如果每次加法都飽和（像 D-002 的單顆神經元那樣），結果會依順序而不同，Python 與 RTL 無法保證逐位元一致。精確求和再飽和一次，結果與順序無關。
- **代價：** 單顆神經元的 D-002（逐次飽和）與網路的「單次飽和」是兩種規則。兩者都寫在模型裡，並有測試區分。
- **延遲：** 與 D-006 一致，第 t 步的發放在第 t+1 步才進入突觸輸入。

## D-009 突觸權重縮放 w_shift（M3）

- **決定：** `w_shift` 是網路層級的全域常數（MVP 為 2），不是每個突觸或每顆神經元各自設定。權重為 8-bit 有號整數，貢獻為 `w << w_shift`（Q8.8 原始值）。
- **理由：** 8-bit 權重最大 127，左移 2 位後為 508，約等於 2.0，足以讓一個發放者在典型參數下推動神經元接近閾值。全域常數讓硬體不需要每個突觸的額外位移暫存器。
- **代價：** 權重的動態範圍固定。若之後需要不同的增益，必須重新決定常數（或改為網路參數暫存器）。
- **狀態：** 已審閱（2026-11-06）。M3 之後若要調整增益，先改這裡與 `model/network.py`，再改 RTL。

## D-010 網路記憶體組織：單埠同步讀取與雙累加器（M3）

- **決定：** 網路的每塊記憶體（狀態、外部輸入、權重、發放旗標、突觸累加器）只有一個寫埠與一個同步讀埠，讓綜合器映射成 BSRAM。突觸累加器用兩塊交替（`par`）：本步讀 `cur`、寫 `nxt`，下一步對調。階段 A 與 B 做成流水線，讀取位址提前一拍送出。
- **理由：** 陣列寫法在 N = 256 時綜合成約 45,000 cells，因為記憶體變成正反器，超過晶片的邏輯資源。BSRAM 每埠一次一個位址、讀取有固定延遲，單埠讀寫符合硬體。兩塊累加器讓讀取的是本步輸入、寫入的是下一步輸入，不需要搬移資料，也不需要在讀取前清零。
- **代價：** 讀取固定延遲一拍，流水線排程要考慮它。流水線依賴「連續兩次讀取的目標不同」這個性質（見 `docs/EXPLAIN.md` 4.17），以後若改排程順序，要重新檢查。
- **狀態：** 已審閱（2026-11-06）。N = 256 模擬已與模型逐位元一致（51,200 筆）。完整設計的 place-and-route 已通過（`make TOP=network_top`，區塊記憶體 45/46，布線後 38.75 MHz，見 `docs/EXPLAIN.md` 4.18、4.20）。板上結果已有（N = 256 流程測試與 5 個 E/I 條件，全部逐位元一致）。（早期的測試外殼數字 35/46、785 LUT4 已不再適用。）

## D-011 網路命令、payload 緩衝與讀回方式（M3 完整設計）

- **決定：** 新增四個命令：WRITE_WEIGHTS（0x02）、SET_INPUT（0x03）、READ_COUNTS（0x07）、READ_SNAPSHOT（0x08）。decoder 把整個 payload（最多 255 bytes）緩衝，checksum 通過後才寫入。讀回的是每顆神經元的發放次數（16-bit）與最後一步的快照（V、spike）。逐步的 spike 軌跡另由 READ_TRACE（0x09）讀回，見 D-013。`busy` 為高（回覆、複製或網路執行中）時，所有命令都被拒絕，包括 WRITE_PARAM。
- **理由：** 權重一次最多 253 個，16-byte 緩衝不夠。逐步紀錄在 N = 256、1024 步時需要約 4.4 Mbit，超過 GW2AR-18 的區塊記憶體（約 828 Kbit）；計數器與快照只需要 N × 33 bit。執行中改參數或權重會讓結果不可重現，所以 WRITE_PARAM 也要被擋下。
- **代價：** 只有計數與最後一步的快照時，看不到中間步的軌跡（後來加上 spike 軌跡，見 D-013）。decoder 的緩衝從 16 增加到 255 bytes，佔用更多邏輯。READ_RECORD 在網路版沒有回覆，但仍被 decoder 計為 ok，所以 host 必須避免送它。READ_TRACE（0x09）在 `neuron_top` 與 `cmd_test` 的版本也沒有回覆，同樣被計為 ok。
- **狀態：** 已審閱（2026-11-06）。N = 16、64、256 的位元組層級模擬都已與模型一致。N = 256 已燒上板，682 個封包（含 READ_TRACE）的流程測試全部一致（見 `docs/EXPLAIN.md` 4.18、4.20）。E/I 的 5 個條件也已上板一致。

## D-012 E/I 實驗的網路設定與功能驗證方式（2026-11-04）

- **決定：** E/I 實驗用 `w_max = 10`、`e_max = 30`、N = 256、600 步（前 100 步不計），只變動抑制來源的比例 f_inh。`w_max` 是生成網路時的參數，不改 RTL，也不改 `w_shift`。
- **理由：** `w_max = 60` 時網路不是沉默就是飽和（發放率 0.33 = 不反應期上限），外部輸入的影響消失，無法做擾動實驗。`w_max = 10` 下 f_inh 的效果單調且清楚（見 `docs/EXPLAIN.md` 4.19）。
- **功能驗證：** 網表模擬在這個工具鏈無法完成（Gowin 區塊記憶體模擬模型是空的）。以上板結果作為功能驗證：N = 256 的完整流程（682 個封包，含 READ_TRACE）與 E/I 的條件都與完整模型逐位元一致。
- **更正（2026-11-04）：** 早期的 E/I 上板執行（662 個封包）用的網路，其 ext 向量來自另一組亂數抽取（`random.Random` 在生成 W 之後的抽取順序不同，見 `docs/EXPLAIN.md` 4.19）。目前的生成器（`ei_full_sweep.build`）重新產生的網路，發放率與那批舊執行不同（0.246 與 0.138，而不是 0.238 與 0.144）。現在的 5 個條件都以目前的生成器重跑並通過；舊的 662 個封包執行不是用目前網路重跑的，所以不能說同一個網路已被驗證。
- **代價：** 完整掃描（2026-11-04）加入了 w_inh、w_max、e_max，共 24 組，全部單調（見 `docs/EXPLAIN.md` 4.19）。上板的有 5 個條件（含 w_inh = 0.5、2.0 與 w_max = 20），全部與完整模型逐位元一致。`w_max` 不是生理校正值，E/I 的結論只能說到「模型中」，不能直接說到生物。
- **狀態：** 已審閱（2026-11-06）。

## D-013 逐步 spike 軌跡：每步每顆一個 bit，最多 512 步（2026-11-04）

- **決定：** 每一步的所有神經元的 spike 都存進板上的 block RAM，每步每顆神經元 1 bit，一個 byte 放 8 顆。最多保留一次 RUN 的前 512 步。讀回用 READ_TRACE（0x09）：start（步的索引，2 bytes）、count（1..7 步，1 byte）。回覆每步 N/8 bytes，第 b 個 byte 的第 j 個 bit 是神經元 8b+j。讀取範圍必須在 min(run_len, 512) 之內，否則拒絕。**只存 spike，不存 V**。V 只有最後一步的快照（D-011）。
- **理由：** 每步的 V 與 spike 在 N = 256 時是 17 bit × 256 = 4,352 bit，只能存約 40 步，不夠用。只存 spike 是 256 bit/步，512 步約 128 Kbit，GW2AR-18 的 block RAM 還剩約 9 塊（約 160 Kbit）。實際映射後軌跡用了 8 塊，總計 45 / 46，place-and-route 通過（見 `docs/EXPLAIN.md` 4.20）。用 8 bit 寬的記憶體（深度 512 × N/8）而不是 256 bit 寬，讓綜合器比較容易映射，也不需要 256 個 FF 當暫存列。步的位址用 `steps_done`，在最後一筆紀錄的同一個時脈寫入，不需要額外的計數器。
- **代價：** (1) 超過 512 步的 RUN 只保留前 512 步。E/I 的 600 步實驗因此只能讀回前 512 步的 spike，後面 88 步的 spike 只有計數。(2) 沒有 V 的逐步軌跡。網路每次 RUN 都從靜止開始，所以要得到第 k 步的 V，只能 RUN k 步再讀快照，每個 k 都要從頭跑一次。這做得到但很慢，目前沒有做。所以「逐步比對」的範圍是 spike，不是 V。(3) 這把 block RAM 用到接近上限（見 `docs/EXPLAIN.md` 4.20 的資源數字），之後若要加功能，要先算空間。
- **驗證：** 模擬 N = 16（T = 200 與 T = 600，後者測 512 的上限與 off-by-one）、N = 64、N = 256（T = 200，682 個封包）的位元組層級比對全部 PASS。變異測試四個都 FAIL（bit 順序、步位址差 1、上限 513、count 上限 8）。板上用 `host/ei_board_test.py` 跑五個 E/I 條件，每個 745 個封包（1 個開始的 READ_STATUS、1 個 WRITE_PARAM、656 個 WRITE_WEIGHTS、3 個 SET_INPUT、1 個 RUN、1 個 READ_STATUS、4 個 READ_COUNTS、4 個 READ_SNAPSHOT、74 個 READ_TRACE），前 512 步的 spike 與 `run_network` 逐位元一致。（先前寫的 736 是腳本的列印總數，漏了開始的狀態讀取與 8 個計數/快照封包，腳本已修正。）
- **狀態：** 已審閱（2026-11-06）。
